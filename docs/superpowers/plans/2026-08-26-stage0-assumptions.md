- LlamaIndex rework: entities extracted onto a node live in `node.metadata[KG_NODES_KEY]` where `KG_NODES_KEY == "nodes"` (from `llama_index.core.graph_stores.types`); `SchemaLLMPathExtractor._aextract` always sets this key (to `[]` at minimum) once it runs, so a genuinely absent key only happens if extraction never ran at all (e.g. a broken/misused extractor) — `extract_methods_li` treats that as a hard error (`RuntimeError`) rather than an empty result, per the plan's requirement to fail loud instead of silently returning `[]`.
- LlamaIndex rework: `kg_validation_schema` uses the extractor's "backwards-compat" dict format (checked via `kg_validation_schema.get(subject_type, [relation])`), not the newer `{"relationships": [...]}` triple-list format — confirmed by reading `_prune_invalid_triplets` in `schema_llm.py`. SUPERSEDED below: the single-entity-type `{"METHOD": ["USES_METHOD"]}` version of this schema turned out to be structurally broken (see next bullet); the format choice itself (backwards-compat dict) is still correct and unchanged.
- LlamaIndex rework: constructing `llama_index.llms.anthropic.Anthropic(model=...)` does not touch the network or validate an API key — verified by reading `llama_index/llms/anthropic/base.py` (it stores a lazy `anthropic.Anthropic(api_key=api_key, ...)` client, same lazy-construction pattern as our own `AnthropicLLM`) and by constructing it directly with `ANTHROPIC_API_KEY` unset, which succeeded. This made a real (non-mocked) `build_extractor(...)` smoke test safe to include in `test_li_extraction.py` — it only asserts on the constructed object's config (`strict`, `kg_validation_schema`, `raise_on_error`, `max_triplets_per_chunk`), never calls it.
- LlamaIndex rework, quality fix: the original `entities=Literal["METHOD"]` / `kg_validation_schema={"METHOD": ["USES_METHOD"]}` schema structurally drops talks with a single (or otherwise unpaired) method. `SchemaLLMPathExtractor` only surfaces entities that appear in a *valid* triplet, and `_prune_invalid_triplets` prunes any triplet where `subject.lower() == obj.lower()` (self-reference) — with only one entity type, a lone method has no distinct partner to form a valid METHOD--USES_METHOD-->METHOD triplet with, so it never reaches `KG_NODES_KEY` at all. Fixed by introducing a second, fixed entity type: `entities=Literal["WORK","METHOD"]`, `kg_validation_schema={"WORK": ["USES_METHOD"]}`, with `EXTRACT_PROMPT` instructing the LLM to always emit the subject as a single node named "THIS_WORK" and the object as the METHOD. A lone method now forms a valid WORK->METHOD triplet regardless of how many other methods are present. `extract_methods_li`'s harvesting logic was unchanged (already filtered to `entity.label == "METHOD"`, so WORK entities are already ignored) — pinned with a new regression test using a fake WORK+single-METHOD annotation.
- LlamaIndex rework, hardening: confirmed `raise_on_error` and `max_triplets_per_chunk` are the exact installed parameter names (`schema_llm.py` lines 142/160/157) — no deviation. Set `raise_on_error=True` in `build_extractor` so malformed LLM output raises instead of silently checkpointing as a false "0 methods" result, and `max_triplets_per_chunk=25` explicitly rather than relying on the library's silent default of 10.
- LlamaIndex rework, hardening: `run_stage0.py` now calls `build_extractor(EXTRACT_MODEL)` fresh inside the per-talk checkpointed lambda instead of building one extractor once outside the loop. `SchemaLLMPathExtractor.__call__` does `asyncio.run(...)` per invocation; reusing one `Anthropic` LLM's underlying httpx client across separate event loops (a fresh one per `asyncio.run` call) is a known unsafe pattern for async HTTP clients bound to a loop at first use. Construction is cheap and fully offline, so paying it per-talk has no real cost.
- Live-run note: do a 2-3 talk smoke first; if loop issues appear anyway, switch the loop to a single `asyncio.run(...)` driving `extractor.acall(...)` directly instead of relying on `SchemaLLMPathExtractor.__call__`'s per-call `asyncio.run`.
