# Stage-0 assumptions log

- Task 1: Added `pipeline/.gitignore` (excluding `.venv/`, `__pycache__/`, `*.pyc`, `.pytest_cache/`, `*.egg-info/`) — not in the literal Task 1 file list, but `uv run` created a `.venv` and `.pytest_cache` in `pipeline/` and committing them would bloat the repo with generated/environment-specific artifacts. `uv.lock` (also uv-generated) was left tracked since lockfiles are meant to be committed for reproducible installs.
- LlamaIndex rework: imported `SchemaLLMPathExtractor` from the public `llama_index.core.indices.property_graph` package rather than the deep `...transformations.schema_llm` module — the deep path is where I read the source to verify signatures, but the package `__init__` re-exports the class as public API, which is the stable import surface across versions.
- LlamaIndex rework: `extract_prompt` (installed version 0.14.24) IS customizable — constructor accepts `Union[PromptTemplate, str]`, and `astructured_predict` calls `self.extract_prompt.format(text=..., max_triplets_per_chunk=...)` where unused placeholders are simply ignored (verified empirically) and a missing `{max_triplets_per_chunk}` placeholder is fine, but `{text}` must be present or the abstract/title content is silently dropped from what the LLM sees. Used the exact quality-lever wording supplied in the task plus a trailing "-------\n{text}\n-------\n" body matching the library's own `DEFAULT_SCHEMA_PATH_EXTRACT_PROMPT` shape.
- LlamaIndex rework: entities extracted onto a node live in `node.metadata[KG_NODES_KEY]` where `KG_NODES_KEY == "nodes"` (from `llama_index.core.graph_stores.types`); `SchemaLLMPathExtractor._aextract` always sets this key (to `[]` at minimum) once it runs, so a genuinely absent key only happens if extraction never ran at all (e.g. a broken/misused extractor) — `extract_methods_li` treats that as a hard error (`RuntimeError`) rather than an empty result, per the plan's requirement to fail loud instead of silently returning `[]`.
- LlamaIndex rework: `kg_validation_schema = {"METHOD": ["USES_METHOD"]}` uses the extractor's "backwards-compat" dict format (checked via `kg_validation_schema.get(subject_type, [relation])`), not the newer `{"relationships": [...]}` triple-list format — confirmed by reading `_prune_invalid_triplets` in `schema_llm.py`; with a single entity type and single relation this format is sufficient and matches exactly what the task plan specified.
- LlamaIndex rework: constructing `llama_index.llms.anthropic.Anthropic(model=...)` does not touch the network or validate an API key — verified by reading `llama_index/llms/anthropic/base.py` (it stores a lazy `anthropic.Anthropic(api_key=api_key, ...)` client, same lazy-construction pattern as our own `AnthropicLLM`) and by constructing it directly with `ANTHROPIC_API_KEY` unset, which succeeded. This made a real (non-mocked) `build_extractor(...)` smoke test safe to include in `test_li_extraction.py` — it only asserts on the constructed object's config (`strict`, `kg_validation_schema`), never calls it.
